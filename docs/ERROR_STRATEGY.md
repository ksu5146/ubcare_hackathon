# 에러 처리 · 캐싱 · 성능 전략

---

## 1. 에러 처리 전략

### 1.1 API Route (서버 측)

모든 Route Handler는 try-catch로 감싸며, 성공/실패 여부를 구조화된 형태로 반환한다.

```ts
// 성공
return Response.json({ success: true, data: result });

// 실패
return Response.json(
  { success: false, error: '단지 정보를 불러오지 못했습니다: DB 연결 실패' },
  { status: 500 }
);
```

- 에러 메시지는 **원인 + 맥락** 형식을 따른다: `"[작업 설명]: [실패 이유]"`
- `status` 코드를 명시하여 클라이언트가 에러 종류를 구분할 수 있도록 한다
- 복구 불가능한 에러(예: 스키마 초기화 실패)는 상위로 전파하고 프로세스를 종료한다
- 복구 가능한 에러(예: 단일 지역 수집 실패)는 catch 후 로깅만 하고 다음 작업을 계속한다

### 1.2 외부 API 호출

`lib/api-client.ts`의 `fetchWithCache`가 타임아웃과 재시도를 통합 처리한다.

| 항목 | 정책 |
|------|------|
| 타임아웃 | 10초 (AbortController) |
| 재시도 횟수 | 기본 3회, ODsay 429(Rate Limit) 대응 시 4회 |
| 재시도 간격 | 지수 백오프 (1s → 2s → 4s) |
| 실패 시 반환 | 캐시된 데이터가 있으면 만료 데이터라도 반환 (stale-on-error) |

ODsay API는 분당 호출 한도가 낮아 429 응답 시 Retry-After 헤더를 읽고 대기 후 재시도한다.

### 1.3 DB 에러 (libSQL / Turso)

- 연결 실패: graceful degradation 적용. DB 없이 동작 가능한 기능(예: 필터 UI)은 정상 렌더링하고, DB 의존 기능만 에러 상태로 표시한다.
- 쿼리 실패: 개별 쿼리 단위로 try-catch하여 해당 섹션만 에러 상태로 처리한다. 페이지 전체가 중단되지 않도록 한다.
- 마이그레이션 실패: 컬럼 누락 등 스키마 불일치는 `ALTER TABLE` 자동 보정 후 재시도한다(예: `user_comparisons.type` 컬럼 자동 추가).

### 1.4 클라이언트 에러 처리

- **ErrorState 컴포넌트**: API 호출 실패 시 사용자 친화적 메시지와 재시도 버튼을 표시한다.

  ```tsx
  <ErrorState
    message="단지 정보를 불러오지 못했습니다."
    onRetry={() => refetch()}
  />
  ```

- **글로벌 에러 경계**: `app/error.tsx` — 예상치 못한 렌더링 오류를 포착하여 전체 화면 에러 UI로 표시한다.
- **404 처리**: `app/not-found.tsx` — 존재하지 않는 단지/경로 접근 시 안내 메시지와 홈 링크를 제공한다.
- 에러 발생 시 사용자에게는 간결한 메시지를, 개발자를 위한 상세 스택은 서버 콘솔에만 기록한다.

## 2. 캐싱 정책

### 2.1 인메모리 캐시 (`lib/cache.ts`)

서버 프로세스 내 `Map` 기반 캐시. 서버리스 함수 재시작 시 초기화된다.

| 데이터 종류 | TTL | 근거 |
|-------------|-----|------|
| 실거래가 조회 결과 | 24시간 | 공공 API 데이터는 일 단위 갱신이므로 당일 반복 조회 시 API 호출 불필요 |
| 단지 기본정보 | 7일 | 단지 메타데이터(주소, 세대수 등)는 거의 변하지 않음 |
| 학교·인구 등 정적 데이터 | 30일 | 연 단위 변경되는 정적 정보 |

캐시 키는 `[엔드포인트]:[파라미터 해시]` 형식으로 구성하며, hit/miss 여부를 서버 콘솔에 로깅한다.

### 2.2 DB 캐시 (`geocode_cache` 테이블)

카카오 지오코딩 API 결과를 DB에 영구 저장한다.

- **목적**: 동일 주소에 대한 반복 지오코딩 API 호출 방지
- **키**: 정규화된 주소 문자열
- **만료**: 없음 (주소-좌표 매핑은 사실상 영구 불변)
- **조회 순서**: DB 조회 → 미스 시 카카오 API 호출 → 결과를 DB에 저장 후 반환

### 2.3 클라이언트 캐시

- SWR/React Query 패턴을 사용하지 않는다. 페이지 전환 시 데이터를 재조회한다.
- 즐겨찾기·비교분석은 `localStorage`에 클라이언트 상태를 유지하며, 로그인 시 DB와 병합한다.
- 필터 북마크는 `localStorage`에 영구 저장한다(`hooks/use-filter-bookmarks.ts`).

## 3. 성능 전략

### 3.1 지도 렌더링 — 뷰포트 기반 마커 컬링

`components/map/KakaoMap.tsx`에서 현재 지도 뷰포트 범위 밖의 마커는 `setMap(null)`로 DOM에서 제거한다.

- 검색 결과 수백 개의 마커를 전부 렌더링하면 카카오맵 SDK의 DOM 조작 부담이 급증한다.
- 뷰포트 기반 컬링으로 화면에 표시되는 마커만 활성화하여 렌더링 비용을 줄인다.
- 줌 레벨 변경·지도 이동 이벤트에서 컬링을 재계산한다.

### 3.2 DB 성능 — WAL 모드 + 인덱스

| 항목 | 설정 |
|------|------|
| 저널 모드 | WAL (Write-Ahead Logging) — 읽기/쓰기 동시성 향상 |
| 인덱스 수 | 11개 (법정동코드, 단지코드, 거래년월, 단지명, 좌표 등) |
| 주요 쿼리 패턴 | trades JOIN complexes WHERE lawdCd + dealYmd 범위 필터 |

WAL 모드는 읽기 트랜잭션이 쓰기를 차단하지 않아 수집 작업과 서비스 조회가 동시에 가능하다.

### 3.3 번들 최적화

`next.config.ts`의 `optimizePackageImports`로 트리쉐이킹이 어려운 대형 패키지의 임포트를 최적화한다.

```ts
experimental: {
  optimizePackageImports: ['recharts', 'lucide-react', '@radix-ui/react-icons'],
}
```

- **recharts**: 차트 컴포넌트를 named import로 사용해도 전체 번들이 포함되는 문제를 방지한다.
- **lucide-react**: 아이콘 수백 개 중 사용하는 것만 번들에 포함되도록 한다.
- **@radix-ui**: UI 프리미티브 개별 패키지의 공통 의존성을 중복 없이 공유한다.

### 3.4 이미지 최적화

현재 서비스는 텍스트 기반 UI로 구성되어 있으며 이미지 에셋을 사용하지 않는다. 향후 단지 사진 등 이미지 추가 시 Next.js `<Image>` 컴포넌트와 Vercel Image Optimization을 사용한다.

### 3.5 Vercel Cron 증분 수집

- 매 1시간 라운드 로빈 방식으로 6개 지역씩 증분 수집한다.
- 전체 66개 지역을 약 11시간에 걸쳐 순환하여 데이터 최신성을 유지한다.
- 수집 상태를 DB의 `collector_state` 테이블에 기록하여 중단 후 재개가 가능하다.

## 4. 에러 처리 · 캐시 · 성능 결정 요약

| 계층 | 주요 결정 | 트레이드오프 |
|------|-----------|-------------|
| API Route | 구조화 에러 응답 `{ success, error }` | 모든 라우트에 일관된 포맷 적용 필요 |
| 외부 API | 10초 타임아웃 + 최대 4회 재시도 | 재시도 중 응답 지연이 사용자에게 노출될 수 있음 |
| DB | graceful degradation | DB 없이 빈 결과를 반환하면 사용자가 문제를 인지 못할 수 있음 |
| 인메모리 캐시 | TTL 기반 Map | 서버리스 재시작 시 캐시 소멸, 첫 요청은 항상 API 호출 |
| 지오코딩 | DB 영구 캐시 | 주소 변경 시(행정구역 개편 등) 캐시 무효화 수동 처리 필요 |
| 지도 마커 | 뷰포트 컬링 | 빠른 지도 이동 시 마커 깜빡임 발생 가능 |
